# Correction Persistence and Functional Regression in LLM-Based Software Agents

## Abstract

Large language model (LLM) software agents repeatedly edit and test code. Later actions can cause previously verified code to lose functional correctness. Prior work has reported cases in which repeated edits broke working code, and evaluating the final submitted patch provides limited insight into when the code broke or whether it recovered. This study measures correction persistence, the first functional regression, and recovery after agents resume from a functionally correct state. It also examines how correctness feedback at resumption affects these outcomes. The study uses a reference patch from SWE-bench Verified to establish a repository that passes the official evaluation, resumes the agent repeatedly from the same execution history, and evaluates the resulting repository states against common functional criteria. In a pilot on one Astropy task, four of five continuations diverged from the reference patch, and four failed the final official evaluation. These findings motivate direct evaluation of intermediate states to identify the first regression and subsequent recovery. The proposed procedure can help study when to run regression tests during continued agent editing.

**Keywords　LLM-Based Software Agents, Oracle-Based Initialization, Correction Persistence, Functional Regression, Correctness Feedback**

## 1. Introduction

LLM-based software engineering agents receive an issue, locate relevant files, modify code, and run tests. The language model chooses the next action based on the task instructions and the results of previous actions, and the agent executes it in the repository (Yang et al., 2024). Code that passes its tests becomes the starting point for further work. If an edit intended to refine the implementation or change another file causes a previously passing test to fail, additional repair and verification are needed. **For long-running tasks, reliability depends on an agent's ability to resolve the issue and preserve verified functionality during subsequent work.**

The effect of repeated revision can depend on how agents evaluate their own output. Madaan et al. (2023) introduced Self-Refine, in which a model evaluates its initial response and refines it using its own feedback. Huang et al. (2024) found that asking models to reconsider answers without external evidence can reduce accuracy on reasoning tasks. Gou et al. (2024) proposed CRITIC, which uses external tool results to improve responses. **Together, these studies show how evidence available during revision can shape its outcome.** For agents that edit repositories, this raises a further question. Once an adequate fix is in place, can the agent assess the current state and preserve verified functionality?

Work on coding agents has examined a closely related problem. **Kim et al. (2026) introduced TRAJEVAL to analyze execution histories and reported cases in which agents produced code matching a reference patch and broke it through further edits.** They also evaluated interventions that preserve and restore code at a selected point in a run. This gives a direct basis for studying functional regression. The present study repeatedly resumes an agent from a repository that passes the official evaluation and from the same execution history. Holding the starting code and prior history fixed makes it possible to observe how test results vary across continuations. Different implementations can pass the same functional evaluation, so code divergence from the reference patch and functional test results are recorded separately.

SWE-bench uses real GitHub issues and their repositories to evaluate whether an agent's submitted patch passes the required tests (Jimenez et al., 2024). The final evaluation shows whether the run ended with the issue resolved. **A run that passes at the end may have failed and recovered midway, and a run that fails at the end may have retained working code until a late change.** Distinguishing these paths helps identify when to verify the code. For example, if regressions are often observed just after further edits, testing after those changes can be evaluated. This requires retaining repository states at model calls or code changes and applying shared criteria to the saved states.

External information may play different roles before and after an issue is resolved. ORACLE-SWE examined how information such as reproduction tests, regression tests, and edit locations contributes to final task resolution (Li et al., 2026). Here, the intervention informs the agent that the repository passed the designated tests at the time of resumption. **This information may help the agent distinguish earlier failures in its execution history from the current state and reconsider whether further edits are needed.** Whether that guidance reduces regressions after subsequent edits is an empirical question. The comparison uses the same repository and execution history in both conditions and varies whether the agent receives explicit confirmation that the tests passed.

**The first research question asks how often verified functionality persists after resumption, how many model calls occur before the first observed failure, and how many runs recover after a regression. The second asks how confirmation that the tests passed affects correction persistence, regression frequency, time to first regression, and recovery.** Measuring when functionality is lost and restored adds information to the final task outcome and helps identify where intermediate verification and feedback could be applied.

## 2. Methods

**The study uses SWE-bench Verified, a benchmark built from real GitHub issues (OpenAI, 2024). The pilot uses the Astropy task astropy__astropy-13033 in an isolated Docker environment with mini-SWE-agent v2.4.6 and GPT-5.4-nano.** The first 42 messages of the original run were restored, and the agent resumed from a repository with the benchmark's reference patch, known as the Gold Patch. The initial repository passed the official SWE-bench evaluation. Oracle-based initialization refers to the evaluator establishing this starting state with the reference patch. The pilot included a message reporting the repository update and passing tests. **The continuations recorded model calls, commands and their outputs, and code changes. These records were used to tally divergence from the reference patch and final official evaluation outcomes.**

The independent variable in the follow-up experiment is whether explicit correctness feedback is given at resumption. For each task, repeated runs use the same initial repository, execution history, model and agent settings, and model-call limit. Both conditions receive a common message that the repository was updated. The feedback condition also receives confirmation that the code passed the designated tests at resumption. **Independent of the tests the agent runs, the evaluator saves repository states immediately after code changes and at the end of each run and applies the same official evaluation criteria.** Reviewing changes and test logs around the first failure helps identify which action preceded the change of state.

The unit of analysis is one continuation. Each evaluated state is recorded as a pass, a functional failure, or undetermined. **Correction persistence is the proportion of runs that pass at every required evaluation point. Functional regression is the proportion with at least one observed failure after the initial pass. Time to first regression is measured in model calls from resumption to the first observed failure. Recovery is the proportion of runs with a regression that subsequently pass again.** States that cannot be evaluated because of environment errors or missing records are counted separately. When observations are missing, the analysis reports the uncertainty between the first observed failure and its actual onset. The follow-up will report differences by task, together with the observed run counts and denominators.

## 3. Results and Discussion

The initial repository containing the reference patch passed the official SWE-bench evaluation for the Astropy pilot task. **Five continuations used the same execution history. Four produced code that differed from the reference patch, and the final official evaluation passed one submitted patch and failed four.** The reported 80% figures describe reference-patch divergence and final evaluation failure, respectively. Final outcomes varied across repeated runs on the same task and starting conditions.

Reference-patch divergence helps identify when code changed. A separate functional evaluation is needed to determine whether the code still met its requirements immediately after a change. A different implementation that still passes the same tests retains the observed functionality. When the same official evaluation changes from pass to fail, the result indicates a loss of correctness under those criteria. The final failures in the pilot show that runs can start from a verified state and end in failure. Evaluation of intermediate states is needed to identify the edit after which failure first occurred and any intervals in which a temporary failure was followed by a pass.

In some runs, local tests performed by the agent passed during execution, while the submitted patch failed the final official evaluation. The assessments may have differed in test coverage and repository state. Local tests may have checked only some behavior, leaving a problem detectable by the official tests. A subsequent edit may also have introduced a problem after the local tests passed. Applying the same official tests to the saved state immediately after the local pass and to later states would help distinguish these explanations.

The sample and initialization method limit what can be inferred. Four of five is an observation from one issue, execution history, model, and agent configuration. Repeating runs would show how much the outcomes vary within the task, and adding tasks from other repositories would support comparisons across issues. Applying the reference patch fixes the starting code, while the earlier history may contain exploration or failures that no longer reflect the updated repository. This mismatch may shape subsequent edits, which is why both conditions receive the same repository update notice. **The effect of correctness feedback can be assessed once outcomes are collected for both conditions under matched starting conditions.**

## 4. Conclusion and Implications

This study proposes an evaluation procedure that resumes a software engineering agent from a repository that passed the official evaluation and tracks whether verified functionality persists, is lost, or is restored. In the single-task Astropy pilot, the initial repository passed while four of the five continuations failed the final evaluation. Recording initial and final results together helps identify when a run ends with a loss of previously verified functionality.

**The study extends the evaluation of agents' problem-solving ability to include their ability to preserve a verified fix.** Identical starting repositories led to different final outcomes, and explaining this variation requires information about when edits and verification took place. Follow-up work can examine the relationship between decisions to continue editing and functional persistence. Comparing runs where an agent relies on an earlier failure with runs where it ends the task based on a current pass can show what information shaped its decision.

The analysis uses reference-patch divergence, intermediate functional evaluation, and final evaluation for different purposes. Divergence identifies where code changed. Intermediate evaluation checks test outcomes after changes, and final evaluation records whether the functionality was present at the end. Recording undetermined states distinguishes observed failures from gaps in the record. Future work could also follow runs from the point at which an agent's own patch first passes the official evaluation, allowing comparison with reference-patch initialization.

**For software teams, the procedure offers a way to evaluate whether retaining a verified state and rerunning the same tests after further agent edits helps detect regressions.** Saving a restorable passing state and comparing test results after an edit can help narrow down the changes associated with a problem. Running the official evaluation after every edit increases time and cost, so observations across tasks can inform which changes warrant earlier verification. Whether to include explicit confirmation of a pass in operating procedures can be assessed by comparing regression, recovery, and execution cost across tasks and models.
